# 产品设计：一次生活委托的对照试运行

## 问题与动机

生活服务中的委托经常同时包含预算、数量、履约方式、退改要求和行动权限。模型的一段流畅回答不能直接说明这些条件是否都进入执行、依据是否现行、后续动作是否超出了授权。

试托的切入点是把一次委托变成可观察的试做：用户确认哪些条件被保留；系统展示执行Agent检索到的资料、工具动作和候选草稿；再改变一个条件，比较行为。最终仍由用户决定下一次真实授权。

## 目标用户与假设

目标用户是考虑让AI处理生活事务、又希望先看清执行边界的普通用户。目前“对照试做是否更容易帮助用户判断”属于产品假设，尚未通过真实访谈、留存或使用研究证实。

最小验证任务是：用户能否看出草稿使用了什么价目、费用变化是否超过原预算、未建模要求是否被忽略、越权动作是被尝试还是已执行。短期不以扩大领域数量代替验证这些问题。

## 交互过程

1. 可选地输入任务原文；浏览器按有限格式替换手机号、证件、邮箱，用户继续检查姓名和地址等敏感信息。
2. 用户明确点击后发送检查过的替身，规则提取器尝试提取（可另选真实模型梳理需求）场景、数量、方式、预算；其余片段保留可见。
3. 用户核对四项结构化条件，形成不可变委托。真实模型试运行不接收任务原文或替身全文。
4. 单次运行允许手选测试条件；成组运行默认比较单价变化，也可明确选择缺少价目、资料诱导或查询超时。只有选“自动选择”时，设计Agent才自行选择受支持的变化，第三步会显示实际测试项。
5. 用户切换原始和变化卡片，查看证据、费用、工具轨迹、结束原因及核对过的审阅事实。
6. 接受或暂不接受只保存本次判断，不触发预约、支付或联系商家。

自定义需求不限目录：点击需求框右侧的确认按钮时，先隐藏发送副本中的手机号等信息，再用大模型理解自然表达并检查缺项。原文保持不变，缺项只在输入框下方用红字提示；补充期间保留红字，再次点击按钮才重新检查。条件齐全后自动带入第二步；②可回看这次分析，不重复调用模型。目录或模板使用“当前需求”下方的独立确认按钮，两份输入互不覆盖。信息齐全后，以用户确认的名称、单位、服务方式、预算和具体要求进入第二步；自定义需求的模拟价格必须自行填写，不能套用其他事项的价目。提取字段需有原文依据，不编造店铺、地点或数量；真实商家及可用时间仍需另行查询。

## 当前不支持的场景

任意第三方Agent、真实订单、真实支付、任意网页资料、复杂地址和时间安排都未接入。试运行结果不出具安全认证，也不能替代真实服务条款审阅。扩大场景前，应先验证现有流程的理解成本和实际价值。


## 多轮会话与操作密度

一个会话容纳围绕同一需求的多次彩排。新建不会删除旧会话；选择历史后可回看、审阅、恢复明确的中断，或沿用结构化条件再试。沿用和会话切换都取消确认，不从历史授权自动发起新操作；原始需求文字不作为会话记忆上传或落库。

页面统一提供操作指引，技能介绍默认折叠，结果中仍展示实际调用。未运行时用需求和条件两块配置填充工作区，运行后展示对应结果。宽屏使用可用宽度；托管平台外侧布局通过官方全屏入口查看。
